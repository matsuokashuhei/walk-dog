# Pull Request の作成と更新

## タイトル

- タイトルはプロジェクト文脈やセッション番号なしで変更内容を示す。
- 具体的な名詞と動詞で変更を表す。例: `Add owners table`、`Fix token refresh`。

## PR 本文

PR 本文には次の節を含める。

### Changes

意味のある変更を、ファイルパスと1行の要約でコンポーネントごとに列挙する。

### Verification

実行した検証コマンドと結果を列挙する。

- `npm test` — テスト数と結果
- `npm run check` — lint、jscpd、knip、typecheck の結果

## レビュー対応

- inline comment は対応内容を反映し、解決内容を返信する。
- follow-up 修正は別コミットとして push し、レビュー履歴を保持する。
- 変更内容に合わせて PR 本文を更新する。

## スキル準拠レビュー

ユーザーの依頼を待たず、PR 公開前に次を行う。追加のモデル、担当、観点、承認条件の指定があれば、同じ手順に足す。

- 対象: merge diff（`origin/main`..HEAD）
- 観点: `AGENTS.md` と `.agents/skills/` 配下のすべてのスキル
- 承認: Critical 0 かつ Important 0。再レビューが承認されるまで PR を merge-ready にしない

1. レビュー依頼に、対象 diff、モデル、`AGENTS.md`、全 skill、Critical / Important の判定、承認の完了条件を記載する。
2. サブエージェントにレビューを依頼する。全メッセージをセッション成果物へ保存し、モデル、対象、依頼文、結果を PR 本文にも記録する。
3. 指摘ごとに修正コミットと解決内容を記録し、同じ観点の再レビューを実行する。
4. 最終レビューの承認応答を確認してから PR を ready for review または merge の状態へ進める。

## ライフサイクル

1. 説明的なタイトルと完全な本文で PR を作成する。
2. レビューコメントを確認する。
3. 修正を適用して push する。
4. 各コメントへ解決内容を返信する。
5. すべてのコメントが解決した状態を確認する。
