# エラー応答責務のレイヤー配置

エラー応答の設計では、各レイヤーの責務を明確に区分する。サーバーの横断的レイヤー（フック、ミドルウェア）は汎用的なエラーフォーマットのみ提供し、フィールド固有やユースケース固有のメッセージは下位レイヤーまたはクライアントが担う。

## 責務区分

| レイヤー | 責務 | 例 |
|---|---|---|
| サーバー横断的レイヤー（defaultHook / エラーハンドラー） | 汎用的なエラーフォーマットの提供。リクエスト ID の付与。フィールド非依存の汎用メッセージ。 | `入力内容を確認してください。` |
| ルートハンドラー | ビジネスルール違反のエラー変換。Cognito エラー → API エラー などのマッピング。 | `このメールアドレスは既に登録されています。` |
| クライアント（モバイル / Web） | ユーザー向けメッセージの選択。pre-submit バリデーション。サーバーエラーコード → 表示文言のマッピング。 | email 形式違反 → `メールアドレスの形式が正しくありません。` |

## プロジェクトルール

- サーバーの横断的バリデーションエラーは、フィールド非依存の汎用メッセージのみ返す。特定フィールド向けの個別メッセージを横断的レイヤーに追加しない。
- フィールド固有のユーザー向け文言が必要な場合、クライアントが pre-submit 検証またはエラーコード / フィールドパスから表示文言にマッピングする。
- ルートハンドラーは Cognito などの外部サービスのエラーをアプリケーションエラーに変換する責務を持つが、入力値のバリデーションエラーまでは担当しない（それはグローバルレイヤーまたはクライアントの責務）。

## 判断テーブル

| 状況 | 処理レイヤー | 備考 |
|---|---|---|
| 「メールアドレスの形式が正しくありません」を表示したい | クライアント（pre-submit） | 送信前に JS バリデーションで検出し表示。サーバーエラーのフォールバックは汎用メッセージでよい |
| 「そのメールアドレスは既に登録されています」を表示したい | ルートハンドラー | Cognito の `UsernameExistsException` などをルートハンドラーで変換する責務 |
| サーバーエラーが「入力内容を確認してください」しか返さないので不十分 | クライアント | サーバーが返すエラーコードと field path をクライアントでマッピングする設計を検討する。その場合も横断的レイヤーはフィールド知識を持たず、構造化された issues 情報を返す |
| 予期しないサーバーエラー | サーバー横断的レイヤー | `INTERNAL_ERROR` として汎用メッセージを返す。リトライ可否などの情報を付与する |

## 完了チェック

エラー応答の設計または変更を完了と報告する前に、以下を確認すること：
- 各エラー種別が、責務区分テーブルの適切なレイヤーで処理されていること
- サーバーの横断的レイヤーにフィールド固有のドメイン知識が含まれていないこと
- ルートハンドラーが外部サービスエラーの変換のみを担当し、入力バリデーションを横断的レイヤーと重複して行っていないこと
- クライアントサイドで必要なエラーマッピング方針が定義されていること
