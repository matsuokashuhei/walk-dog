# 横断的関心事とドメイン知識の分離

横断的関心事（cross-cutting concern）のコードを変更する前に、そのコードが特定のフィールド名やユースケースを知る必要があるかどうかを判断すること。横断的コードはリクエスト処理パイプライン全体に適用されるため、そこにドメイン知識が混入すると、ルート追加のたびに修正が必要になり、拡張性が低下する。

## プロジェクトルール

- OpenAPIHono の `defaultHook`、`app.use` ミドルウェア、`app.onError`、`app.notFound` などの横断的レイヤーで、`path.includes('email')` のような特定フィールド名による分岐を禁止する。
- 横断的レイヤーが返すエラーメッセージは、フィールドやユースケースに依存しない汎用メッセージに限定する。
- 特定のフィールドやユースケースに特化した処理が必要な場合、ルートハンドラー内またはクライアントサイドで実装する。

## 判断テーブル

| 状況 | 採るべき設計 | 避けるべき設計 |
|---|---|---|
| 特定のフィールド（例: email）のバリデーションエラーに個別メッセージを返したい | クライアントサイドの pre-submit 検証、またはルートハンドラー内で処理 | defaultHook やミドルウェアでフィールド名を判定して分岐 |
| 複数のルートが異なるエラー表現を必要とする | 各ルートが自身のエラーレスポンスを閉じて持つ | 横断的レイヤーにルートごとの条件分岐を追加 |
| 横断的レイヤーでリクエストの内容に応じた処理が必要 | リクエストヘッダーやパスのパターンマッチなど、プロトコルレベルの情報のみで判断 | リクエストボディのフィールド名や値で判断 |

## 完了チェック

横断的レイヤーの変更を完了と報告する前に、以下を確認すること：
- 横断的コードに特定のフィールド名やユースケースの知識が含まれていないこと
- 新しいルート追加が横断的コードの修正を必要としない設計であること
- フィールド固有の処理が必要な場合、適切なレイヤー（ルートハンドラー / クライアント）に配置されていること
